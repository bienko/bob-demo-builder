Up to this point in the hands-on materials you have operated as a *consumer*: you installed the Demo Builder and briefed it well, then examined the strategy underneath. Sooner or later every practitioner runs up against a gap in the inventory of *Modes* or *Skills* (or *Rules*) available on-hand. It may be a vertical without a *Mode*, a product without a *Skill*, or a team convention with no *Rule* holding it in place.

In these circumstances, **Asset Templates** are the mechanism for filling that gap *without breaking the discipline and organizational rigor* documented in the previous chapters.

Asset templates are the **executable form of the strategy**. Each one encodes its corresponding contract:

- The *Mode* core contract
- The *Skill* design principles and definition of what "completeness" looks like
- The *Rule* principles and definition of what "completeness" looks like

In essence, it provides a **boilerplate** that ensures the assets created conform to an organization's strategy *by construction*, rather than by after-the-fact review.

| TEMPLATE | USE IT TO CREATE |
|----------|------------------|
| `MODE.template.yaml` | a new general or industry mode → `MODES/…` |
| `SKILL.template.md` | a new skill → `SKILLS/<name>/SKILL.md` |
| `RULE.template.md` | a new ambient rule → `rules/rules-<name>/<name>.md` |

!!! note "NAMING CONVENTIONS"
    Why `MODE` versus `Mode` versus `mode`? Naming conventions that IBM Bob applies when generating and recording *asset templates* means that you will often see the *ALL-CAPS* spelling within the IDE. Colloquially and in written documentation, the various forms carry the same meaning.

## **ii. Deciding which asset to build**

---

The most common authoring mistake has less to do with filling in template forms poorly, but rather stems from selecting the wrong template to begin with. Before copying anything, run your idea through the decision tree:

```
"A constraint must always hold (any mode, task)?" → RULE  (global/workspace/mode?)      → SKILL
"How to approach an engagement class"?            → MODE   (vertical & deep?)           → Industry MODE, replaces a general one)
"How to use a product / contract / capability"?   → SKILL  (drives an MCP?)             → SKILL paired with that MCP)
"How to reach a system from Bob"?                 → SDK/CLI (exists & available?)   yes → use it (document in a SKILL)
                                                                                    no  → MCP (last resort) + paired SKILL
```

Recall the litmus tests from the strategy chapter. If a constraint should hold even when nobody asked for it, it is a *Rule*. If it constitutes method for a whole engagement class, it is a *Mode*. If it is product knowledge carrying depth, it is a *Skill*. And reach is documented first as a *Skill* describing an SDK or CLI (with an *MCP* built only as the last resort.)

## **iii. Authoring a Mode**

---

The following information is the **contract**. You can execute the following instruction within a Terminal console to begin crafting your own (if you like).

!!! warning "TERMINAL"
    ``` bash
    cp MODE.template.yaml MODES/<your-mode>.yaml
    ```

Replace every `<...>` placeholder and tailor as necessary to your requirements.

!!! success "*MODE* CORE CONTRACT CHECKLIST"
    1. Clear persona + engagement class (`roleDefinition`, `whenToUse`).
    2. Shared build lifecycle present: intake → mapping → build → document → verify → hand-off.
    3. Shared non-negotiables enforced (runnable artifacts; synthetic data; env secrets; mock works with zero deps; accessibility; honest claims; compliance-before-done).
    4. Decision gates G0–G5 implemented as optioned questions; autonomous between gates.
    5. **References** the skills it depends on — duplicates none of their content.
    6. Ships a self-check script (`check-compliance.sh`, plus `check-carveouts.sh` if it has guardrails).
    7. `slug` is unique and **does not equal any Skill name**.
    8. Industry mode: states it **replaces** a named general mode; adds only vertical KB / guardrails / blueprints / components / stricter synthetic-data.
    9. File parses: `python3 -c "import yaml,sys; yaml.safe_load(open(sys.argv[1]))" MODES/<your-mode>.yaml`

Make the final line a standing practice: run the parse check with every authoring pass. A *Mode* that fails to parse will fail silently in the field.

## **iv. Authoring a Skill**

---

The following information is the **contract**. You can execute the following instruction within a Terminal console to begin crafting your own (if you like).

!!! warning "TERMINAL"
    ``` bash
    mkdir SKILLS/<name> && cp SKILL.template.md SKILLS/<name>/SKILL.md
    ```

Replace every `<...>` placeholder and tailor as necessary to your requirements.

!!! success "*SKILL* DEFINITION OF COMPLETENESS"
    1. Valid cross-runtime frontmatter: `name`, `description`, `metadata.enabled: true`.
    2. `name` is unique and **does not equal any Mode slug**.
    3. `description` is rich with concrete **trigger terms** (drives auto-discovery).
    4. Single responsibility — one product/contract/capability.
    5. Content **verified against a real product version**; the "Verified against X, <date>" stamp is filled in.
    6. Depth pushed to `references/`; `SKILL.md` stays focused (progressive disclosure).
    7. States its paired **MCP / SDK / CLI** (or "none").
    8. No secrets; credentials via env/connection patterns only.

**Two of these items deserve special attention.**

- The **description** is the single most important line in the file. It is what triggers auto-discovery, so write it in the form of *"use this whenever the user mentions or needs X"* and be generous with trigger terms.

- The **verification stamp** is what separates a *structured field manual* from disjointed *notes in the margins*: run the CLI and exercise the API, then record the version and date that the content was verified against.

## **v. Authoring a Rule**

---

A *Rule* is **always-on and brief**. It costs context on every invocation and for each reference back to an LLM's context window, so trim anything optional or redundant. The *Rule* must state *what needs to always hold*; it never teaches a product API (point to a *Skill* instead for that information).

Each *Rule* lives in its own `rules-<name>/` folder so it can be copied individually into `.bob/rules/`. Pick the scope carefully:

- Org-wide → `~/.bob/rules/`
- This project → `<project>/.bob/rules/`
- One *Mode* or vertical → `.bob/rules-{slug}/` (note that `rules-{slug}` at the top of `.bob/` is *mode-specific*)

The following information is the **contract**. You can execute the following instruction within a Terminal console to begin crafting your own (if you like).

!!! warning "TERMINAL"
    ```bash
    mkdir rules/rules-<name> && cp RULE.template.md rules/rules-<name>/<name>.md
    ```

Replace every `<...>` placeholder and tailor as necessary to your requirements.

!!! success "*RULE* DEFINITION OF COMPLETENESS"
    1. Short, imperative, **testable** statements (yes/no per line); whole file ≈ < 15 lines.
    2. Correct **scope** chosen (global / workspace / mode-specific) and reflected in the metadata line.
    3. **No product knowledge** embedded — references a skill for any how-to.
    4. No secrets or credentials.
    5. `Owner` + `Last-reviewed` date filled in; one concern per file.

## **vi. Key takeaways**

---

- Asset templates are the **executable form of an organization's strategy and standards**
- **Choose the asset type first** via the decision tree (choosing the correct template is more important than how it is filled in)
- Modes stay **thin** (method + references)
- Skills carry the **knowledge** (verified, single-responsibility)
- Rules stay **short** (under 15 lines, testable, and scoped)
- Names matter mechanically: mode slugs and skill names must never collide and a skill's `description` is what makes it discoverable to others
